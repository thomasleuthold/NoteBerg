# MCP Server — Implementation Plan

Companion to [DESIGN.md](./DESIGN.md). Ordered so each phase is independently testable and merges without changing existing behavior until the feature is deliberately enabled.

Guiding rule: **the MCP server is off by default and inert until explicitly enabled.** No existing app behavior — startup, storage, sync, recognition — changes while MCP is disabled. Storage code (`storage.js`) is **reused unchanged**; no refactor (DESIGN ADR-001, Alt C).

Guiding rule: **containment.** All MCP logic lives in `src-tauri/src/mcp.rs`, `src/modules/mcpBridge.js`, and (from Phase 5) `src/modules/mcpAuditLog.js`. Touching `lib.rs`, `main.js`, or shared infrastructure (`storage.js`, `logger.js`) beyond a one-line registration needs a specific justification, not convenience — if a phase seems to need more, the right move is usually a new self-contained function/module owned by MCP, not a deeper hook into app startup or existing modules. (This is why the MCP access log got its own dedicated IndexedDB database rather than a new object store in `storage.js`'s shared schema, and its own module rather than extending `logger.js`.)

---

## Phase 0 — Breakthrough slice: one read, all layers (`list_notebooks`)

**Goal:** prove the full vertical path `MCP client → Rust localhost server → webview JS bridge → storage.js → back` with the single cheapest tool. Deliberately **not** spec-compliant MCP yet (DESIGN §4) — plain HTTP + bearer.

1. **Rust server module** (`src-tauri/src/mcp.rs`, `#[cfg(target_os = "windows")]`):
   - `tiny_http` listener bound to `127.0.0.1:<port>`.
   - Managed `Mutex<McpState { enabled, token, pending: HashMap<String, Sender> }>` (mirrors the `RecognitionState` managed-state pattern).
   - One route: `GET /list_notebooks`, requires `Authorization: Bearer <token>`; 401 otherwise.
   - On request: mint `requestId`, park a response channel, `eval` into the webview, await channel with a timeout, write the JSON result.
2. **`mcp_respond` Tauri command** (in `lib.rs`): looks up `requestId`, sends payload through the parked channel. Add to `generate_handler!`.
3. **Start hook:** start the server in `run()`'s `setup()` alongside `spawn_recognition_sidecar`, but **gated `enabled == false` by default** (Phase 0 uses a hardcoded dev token; real token in Phase 2).
4. **JS bridge** (`src/modules/mcpBridge.js`): registers `window.__mcpBridge.handle(tool, id, argsJson)`; for `list_notebooks` calls `getAllNotebooks()` and `invoke('mcp_respond', { id, ok:true, json })`; errors → `{ ok:false }`. No-ops outside a Tauri desktop environment.
5. **Wire-up:** import/init the bridge once in `main.js` **after** `initializeApp()` (post-unlock).

**Test / exit:** with the server hardcoded-enabled in a dev build,
`curl -H "Authorization: Bearer <dev-token>" http://127.0.0.1:<port>/list_notebooks`
returns the user's real notebooks as JSON. Missing/wrong token → 401. App with MCP disabled behaves byte-for-byte as today. **No UI, no real MCP protocol, no other tools.**

## Phase 1 — Round-trip hardening ✅ done

Make the bridge production-safe before adding surface. All work contained in `mcp.rs` (no new touch points in `lib.rs`/`main.js` beyond what Phase 0 already added — see the containment rule above).

- **Concurrency fix:** each inbound request is now handled on its own thread (`std::thread::spawn` per accepted connection), not serially on the accept loop — otherwise the ~10s webview round-trip for one MCP call would block every other in-flight call behind it. Verified live: 5 concurrent `curl` requests all returned 200 with correct, independent, identical notebook data.
- **Request-id fix:** replaced the nanosecond-timestamp id (`rand_u64`) with a monotonic `AtomicU64` counter on `McpState` — the timestamp approach had a real collision risk once requests are handled on concurrently spawned threads (Windows timer granularity can repeat within the same tick). Covered by a unit test spinning up 50 ids under rapid-fire minting and asserting uniqueness.
- **Timeout + clean error propagation:** already correct from Phase 0 (`recv_timeout` + pending-map cleanup on timeout) — re-verified, not changed.
- **Webview-not-ready guard:** investigated whether a faster-than-10s fail was possible (a synchronous "is the bridge ready" probe). Not possible — `WebviewWindow::eval` returns `Result<()>` only for dispatch success, never the script's return value, so there is no way to learn "not ready" faster than the existing timeout without adding a second round-trip command. **Decision: keep the existing bounded 10s timeout** — it's already clean (no panic, clear 504), just not latency-optimal for the narrow startup-race window. Not worth the added surface for a cosmetic improvement.
- **App-lifecycle:** the server thread is spawned once at `setup()` and lives for the process lifetime; Tauri doesn't restart `run()` within a process, so "no orphaned socket on restart" reduces to "process exit kills the thread," which it does. No dedicated shutdown hook added — would be new surface for a scenario that doesn't occur in practice.
- **Unit tests** added in `mcp.rs`'s own `#[cfg(test)] mod tests` (mirrors the existing `lib.rs` pattern): deliver-to-matching-request, unknown-id no-op, late-delivery-after-cleanup no-op, and the concurrent/monotonic-id test above. All pass (`cargo test`).

**Exit:** round-trip is robust under timeout, concurrency, and lifecycle edge cases. Still one tool, still dev-token. Verified via `cargo test` (5/5 passing) and a live concurrent-`curl` smoke test against the running dev app.

## Phase 2 — Enable/disable + token management (real security boundary) ✅ done

Turned the dev toggle into the real off-by-default, token-protected control. Rust changes contained in `mcp.rs` (+ 2 one-line `generate_handler!` registrations in `lib.rs`, per the containment rule); all settings/token logic contained in `mcpBridge.js`; UI added to `settingsMode.js`, placed as its own section immediately after "Handwriting Recognition" (before "Logging"), gated on the same `isWindows` check the recognition section already uses.

- **`McpState.token` is now `Mutex<Option<String>>`** (was a hardcoded dev constant). `None` = no token configured = fail closed, independent of `enabled`. Two new Tauri commands: `mcp_set_config(enabled, token: Option<String>)` (token `None` leaves the stored token untouched — used when only toggling `enabled`; empty string normalizes to `None`, used on revoke) and `mcp_get_status() -> {enabled, has_token, port}` — deliberately never returns the token value itself, mirroring how `get_credential` is treated as write-mostly for secrets elsewhere.
- **Constant-time token comparison** added (`constant_time_eq`) — the token is now a real secret being compared per-request, so a naive `==` (early-exit on first mismatched byte) was worth closing before this became load-bearing.
- **JS is the source of truth, Rust boots stateless.** `mcpBridge.js` owns: `isMcpEnabled`/`setMcpEnabled` (persisted via `storage.js` `getSetting`/`setSetting`, key `mcp_enabled`), `generateAndStoreMcpToken`/`revokeMcpToken`/`hasMcpToken` (persisted via `secureStorage.js` → OS keyring, same path as the master password, key `mcp_token`), and `getMcpStatus`. On `initMcpBridge()` (called post-unlock from `main.js`, unchanged from Phase 0), persisted settings are read and pushed into Rust once via `mcp_set_config` — Rust has no persistence of its own and always starts disabled/tokenless on a fresh process, exactly as before.
- **Token generation**: 256-bit CSPRNG (`crypto.getRandomValues`), hex-encoded — distinct from `storage.js`'s `generateId()` (a 122-bit UUID meant for uniqueness, not secrecy).
- **Settings UI**: toggle (default off, reflects persisted state on render), status line (token configured y/n + port), generate/regenerate button, revoke button (shown only when a token exists). Token is copied to the clipboard *before* the confirmation dialog is shown (not after — `showAlertDialog` only resolves on dismiss, so copying afterward would mean "copied" only once the token was no longer visible) and shown once in a dialog built from DOM nodes (`textContent`, not string interpolation) since the only dynamic content is the freshly generated token itself. Regenerate/revoke both require an explicit confirm dialog first (destructive: breaks any connected client immediately).
- **i18n**: full key set added to `en.json`; the other 8 locales got the same keys with English fallback text (not fabricated translations) via a small verified script — every locale file re-parsed as valid JSON after the edit.
- Port stays fixed (`8765`, matching the recognition sidecar's fixed-port precedent) — no config surface added; revisit only if a real conflict is reported.

**Verified live**, not just by code review: ran the dev app, used the actual Settings UI (human click-through) to enable MCP and generate a token, then confirmed via `curl` against the running server: correct token → 200 with real notebook data; wrong token → 401; no `Authorization` header (even with a token configured) → 401 (distinct from the "no token configured" 503); toggling disable in the UI → immediate 503 even with a still-valid token, confirming `enabled` is checked ahead of the token. Also: `cargo check` clean (only the two pre-existing unrelated warnings), `cargo test` 8/8 passing (added tests for `constant_time_eq`, state defaults, and empty-string-normalizes-to-`None`), `biome lint` clean on the changed files, and the full existing `secureStorage`/`storage` vitest suites (120/120) still pass untouched.

**Exit:** fresh install has MCP off and unreachable. Enabling + generating a token makes the port answer only to that token; disabling immediately makes it refuse regardless of token validity. Token persists across restarts via the OS keyring (not yet re-verified across an actual process restart in this session, but the mechanism is identical to the already-proven master-password keyring round-trip).

## Phase 3 — Real MCP protocol layer (JSON-RPC + transport) ✅ done (protocol-level)

The open item was resolved first by reading the current MCP spec directly (transports, lifecycle, tools pages) rather than assuming: the "Streamable HTTP" transport fits a long-lived process perfectly, POST responses can legitimately always be plain JSON (no SSE required for our fast request/response tool calls), and GET/SSE is spec-legally skippable via 405. All contained in `mcp.rs` per the containment rule — no changes to `lib.rs`/`mcpBridge.js` were needed this phase (the JS bridge's `window.__mcpBridge.handle` contract is unchanged; only the HTTP/JSON-RPC envelope around it changed).

- **Replaced** the Phase 0/1/2 ad-hoc `GET /list_notebooks` REST route with a single `POST /mcp` JSON-RPC 2.0 endpoint — not kept alongside it; verified the old path now 404s.
- **`route_mcp_message`** (pure parse+route, no `AppHandle` needed) handles `initialize` (returns `protocolVersion`/`capabilities: {tools: {}}`/`serverInfo`), `notifications/initialized` (202, no body), `tools/list` (advertises `list_notebooks` with its `inputSchema`), and validates `tools/call` params — split out specifically so all of this is unit-testable without a running Tauri app.
- **`call_tool`** extracted from the old inline Phase 0 logic — reuses the *exact same* `eval_bridge`/`pending`/timeout machinery from Phase 0/1, completely unchanged. `tools/call` results are wrapped as the spec's `{content: [{type: "text", text: ...}], isError}` shape; tool execution failures are reported this way (per spec: "Tool Execution Errors" via `isError:true`), while protocol-level problems (unknown method, bad params, malformed JSON) are real JSON-RPC errors (`-32601`/`-32602`/`-32700`).
- **`Origin` header validation** added ahead of routing: any request carrying an `Origin` header is rejected (403) — closes the DNS-rebinding hole the spec calls out, on the reasoning that legitimate MCP clients (not browser pages) never send `Origin` on a plain HTTP request.
- **9 new unit tests** (17 total in `mcp.rs`, all passing) covering every `route_mcp_message` branch plus the `Origin`-detection helper.
- **Verified live** with a real curl-driven handshake sequence in the exact order a client would send it: `initialize` → 200 correct shape; `notifications/initialized` → 202 empty body; `tools/list` → 200 with the tool descriptor; `tools/call` → 200 with real notebook data through the unchanged bridge; unknown tool → `-32601`; missing `name` → `-32602`; malformed JSON → `-32700`/null id; `GET /mcp` → 405; `Origin` header present → 403; old REST route → 404.

**Real MCP client verification — done.** Connected Claude Desktop end-to-end, not just curl:

- **Claude Desktop's `claude_desktop_config.json` does not support a direct HTTP/URL server entry.** It only deserializes stdio `command`/`args` entries; a `"url"`/`"type": "http"` entry is not merely ignored but has been reported to corrupt the `mcpServers` section entirely. This is a known gap specific to Claude Desktop's config loader (Claude Code CLI's `settings.json` *does* support `type: "http"` directly) — not a limitation of Streamable HTTP itself, and not specific to our server.
- **Researched the precedent** ([Blender's MCP integration](https://github.com/ahujasid/blender-mcp)) before choosing a workaround: Blender faces the identical constraint (a long-lived app with a persistent internal server) and solves it the identical way — a small stdio-speaking shim process (`blender-mcp`, spawned via `uvx`) that proxies to the real, persistent server (Blender's TCP socket addon). This confirmed our architecture isn't a dead end or non-standard; the shim pattern is the normal, spec-compatible way to front a long-lived app's server for stdio-only clients. The one difference: Blender **owns and publishes** their shim; we currently depend on the third-party **`mcp-remote`** package for the same role. Revisit later (not urgent) — if this feature matures, publish our own thin NoteBerg-specific shim instead of depending on an unowned community package.
- **Configured via the `mcp-remote` bridge**: `claude_desktop_config.json` → `mcpServers.noteberg` spawns `mcp-remote` via stdio, which speaks Streamable HTTP to `http://127.0.0.1:8765/mcp`, forwarding the bearer token as an `Authorization` header (`--header "Authorization:Bearer ${NOTEBERG_MCP_TOKEN}"`, token supplied via the config's `env` block, never inlined in `args` where other local processes could read it via a process list). `--allow-http` is required since our endpoint is intentionally plain HTTP on loopback (per DESIGN's TLS-not-needed reasoning).
- **Hit and fixed a real Windows-specific bug**: first attempt failed with `Server disconnected` — the log (`%APPDATA%\Claude\logs\mcp-server-noteberg.log`) showed `cmd.exe` mis-splitting the unquoted `C:\Program Files\nodejs\npx.cmd` path at the space, invoking `C:\Program` as the command. This is a [known, documented issue](https://github.com/modelcontextprotocol/servers/issues/3460): `npx.cmd` is a batch shim that `child_process.spawn` can't invoke directly on Windows. **Fix**: wrap the command as `"command": "cmd", "args": ["/c", "npx", ...]` instead of `"command": "npx"` — the standard community workaround, more robust than hardcoding the full `npx.cmd` path.
- **Confirmed working**: after the fix, Claude Desktop connected, listed `list_notebooks` via `tools/list`, called it via `tools/call`, and correctly rendered all 5 real notebooks (titles, colors, descriptions, versions) in a natural-language response — a genuinely independent client exercising the full stack (Claude Desktop → `mcp-remote` → our `POST /mcp` JSON-RPC server → `eval_bridge` → webview → `storage.js` → back), not a simulated request.

**Exit — fully achieved:** the server correctly speaks JSON-RPC 2.0 over Streamable HTTP for the full `initialize`/`tools/list`/`tools/call` sequence, security properties intact (token, `Origin` rejection), **and** a real, independent MCP client (Claude Desktop) connects and successfully lists/calls `list_notebooks` end-to-end. Still one tool — protocol correctness and real-client compatibility proven before breadth.

## Phase 4 — Remaining read tools

Add the rest of the read surface (DESIGN §1), each reusing existing JS, each registered in `mcpBridge.js`'s `TOOL_HANDLERS` map and advertised in `mcp.rs`'s `tools/list`. Split into two slices since `get_note`'s 7 formats vary a lot in effort (some are plain field reads, one needs new rendering work).

### Phase 4a — `list_notes` + `get_note` (cheap formats) ✅ done

- `list_notes(notebook_id?)` → `getNotesByNotebook()` / `getAllNotes()`.
- `get_note(id, format, media_id?)` → `getNote()`, implementing the formats that are plain field reads (see DESIGN §1 table for the full rationale per format): `metadata`, `text_html` (raw `note.content` HTML, unstripped), `recognized_text` (`recognition.fullText`), `recognized_words` (`recognition.words`, verbatim), `strokes_raw` (`note.strokes`), `media_list` (`note.media` metadata only, no blobs), `media` (one blob from `note.media` selected by `media_id`, base64 data-URI via the existing `fileToDataUrl` helper from `imageUtils.js`).

**Rust side (`mcp.rs`)**: this phase required threading `arguments` (the `tools/call` params object) through the whole pipeline for the first time — Phase 3's `list_notebooks` never needed it. `eval_bridge`, `call_tool`, and `RouteOutcome::CallTool` all gained an `arguments: Value` parameter/field; `tools/call`'s single hardcoded `name != "list_notebooks"` check became a `KNOWN_TOOLS` list shared with the new multi-entry `tool_descriptors()` (was a single-tool function), so the advertised catalog and the "is this callable" check can't drift apart. `arguments` defaults to `{}` when the client omits it (spec-optional). 6 new/updated unit tests (19 total).

**A real bug was caught by the live test, not code review**: the first `list_notes` call failed with `"[object Object]" is not valid JSON`. Root cause: `eval_bridge` builds the `eval` script by embedding `serde_json::to_string(arguments)` directly as a JS *literal* (e.g. `handle("list_notes", "id", {"notebook_id":"x"})`) — the JS side receives a real object, not a JSON string. `mcpBridge.js`'s `handle()` was written assuming a JSON string and called `JSON.parse()` on it, which coerced the object to `"[object Object]"` first. **Fix**: `handle()` now takes `args` as the live object it actually receives — no `JSON.parse` needed. This only surfaced now because Phase 3's one tool (`list_notebooks`) never passed arguments, so the mismatch was latent until the first tool that used them.

**Verified live** against a running dev instance with real note data (not fixtures): `tools/list` advertises all three tools; `list_notes` (both with and without `notebook_id`) returns real note index entries; every `get_note` format tested against a real note with strokes/recognition/media — `metadata` (clean subset, no leaked content), `text_html` (correctly empty for a handwriting-only note), `recognized_text`/`recognized_words` (real OCR output with bounding rects + `strokeIds`), `strokes_raw` (real stroke data), `media_list` (correct metadata-only listing), `media` (real base64 JPEG data-URI for a valid `media_id`). Error paths verified too: unknown `format`, missing `id`, unknown note `id`, missing `media_id` for `format="media"`, and unknown `media_id` — all return clean `isError:true` results, never a crash or hang.

**Exit — achieved:** `list_notes` and `get_note` (all 7 formats) callable from a real running app via curl, each format returns the expected shape, every error path is clean. (Claude Desktop re-verification with the new tools deferred to Phase 4c/end-of-phase-4, not re-run per sub-phase.)

#### Follow-up: two real bugs found by an actual Claude Desktop session (curl testing wasn't enough)

The curl-based verification above was thorough but still missed two real bugs that only surfaced when Claude Desktop actually used `get_note`'s `media` format to look at real attached images — proof that live-client testing catches things spec-conformant unit/curl tests don't:

1. **Wrong MCP content-block type.** The original `media` format returned the image as `{type:"text", text:"{\"dataUrl\":\"data:image/jpeg;base64,...\"}"}}` — a JSON blob *inside a text block*, not the MCP spec's dedicated `image` content type (`{type:"image", data, mimeType}`). Claude Desktop correctly treated it as text-to-process, got stuck trying to save the giant base64 string to a file to inspect it, rather than natively viewing the image. **Fix**: added `to_mcp_content_block()` in `mcp.rs`, which interprets a `__mcp_content_kind` marker (`"image"` | `"audio"` | `"resource"`) that JS handlers can set, and builds the correct MCP wire shape — `image`/`audio` content blocks, or the spec's generic "Embedded Resources" mechanism for `resource` (used for the PDF, since MCP has no dedicated PDF type). Plain results with no marker still become `text` blocks, unchanged. This is Rust *interpreting* an already-computed JS result, not deciding what to fetch — doesn't conflict with `mcp_respond`'s pure-courier invariant.

2. **`media_list`/`media` only covered images — recordings and the imported PDF were silently missing entirely.** A note actually has three separate binary attachment channels: `note.media[]` (images), `note.recordings[]` (audio), and `note.pdfSource` (a single imported-PDF `fileId`, not an array). The original design only exposed the first. **Redesigned and renamed**: `media_list`/`media` → **`attachments_list`/`attachment`**, unifying all three channels into one list with a `kind` field (`"image"` | `"recording"` | `"pdf"`) per entry; `attachment_id` fetches one by id, with the PDF always addressable as `id: "pdf"`. Discovered live: `note.media[]` items whose `type === "pdf-page"` are *bitmap renders of the same PDF* (they share `pdfSource`'s `fileId` — confirmed via `NoteCanvas.js`'s dedup-by-fileId comment), not separate attachments, so `attachments_list` explicitly excludes them — the single `kind:"pdf"` entry already covers that content, and fetching it returns the **original PDF file** (real text/structure) rather than a flattened page image the user asked us to prefer (per discussion: returning the source PDF is strictly better than page images since we already store it and it avoids forcing the client to OCR a raster).

3. **A third, smaller bug found while fixing #1**: `mimeType: image.type || blob.type` used the wrong field — `note.media[].type` is the *canvas-placement kind* (`"image"` vs `"pdf-page"`, per `MediaManager.js`'s own doc comment), not a MIME type at all, so real images were reported with `mimeType: "image"` (invalid) instead of `"image/jpeg"`. **Fix**: use only `blob.type` (the real stored content-type on the file), never the media item's `type` field. Re-verified live: fetched the actual bytes, confirmed valid JPEG magic bytes (`ffd8ffe0`...`ffd9`), decoded and **visually rendered the correct NoteBerg logo image** from a real note — the fix produces a real, viewable image end-to-end.

**Verified live post-fix**: `image` (real JPEG, correct `image/jpeg` MIME, valid magic bytes, visually confirmed as the correct source image), `pdf` (real PDF via the embedded-resource block, correct `application/pdf` MIME, ~8MB blob, addressed via `id:"pdf"`, correctly not duplicated per rendered page). 

**Known issue, tracked, not fixed this session**: the `recording` kind's audio bytes are valid (confirmed real MP3 via magic-byte check `ff fb`) but the reported `mimeType` is unreliable — recordings come from multiple capture paths (browser `MediaRecorder`, native Windows WAV via `native_audio_stop`, and whatever produced this MP3) that don't consistently tag the stored blob's real type; this MP3's blob fell through to `"application/octet-stream"`. Needs magic-byte sniffing or normalizing the type at save time (`RecordingManager.js`) as a proper fix — deliberately not attempted under time pressure in this session to avoid guessing. Flagged with a code comment at the `recording` branch in `mcpBridge.js` and here. **Do not consider `attachment` fully verified for the `recording` kind until this is fixed and re-tested.**

### Phase 4b — `get_note` rendering formats: `strokes_images` + `note_pdf` ✅ done

Scope settled after investigating two existing rendering code paths (both suggested by the user, both real reuse opportunities):

- **`renderNoteSnapshot`** (`utils/noteRenderer.js`) — renders background + media + strokes + text, but is hardcoded to a fixed 360×500 thumbnail box (built for overview cards). **Not reused** — `strokes_images`'s purpose is specifically to give an AI a source image for *handwriting recognition*, so it should render **strokes only**, not media/background/text. `renderNoteSnapshot`'s scope (full note incl. media/text) is a mismatch for that job, not a fit needing adaptation.
- **`exportNoteToPdf(note, mediaItems, onProgress)`** (`modules/pdfExport.js`) — a mature, already-tested full pipeline: real A4 pagination, strokes overlaid on original PDF pages when present, text rendered via `html2canvas`, images placed. Confirmed via `MediaManager.js` that `mediaItems` is just `note.media` (`getItems()` returns `this.mediaItems`, constructed directly from `initialMedia` — no live editor/DOM instance needed), so it's callable directly as `exportNoteToPdf(note, note.media, onProgress)` from the MCP bridge. **Reused as-is, as a new `note_pdf` format** — strictly better than a bespoke full-height PNG for "let the AI see the whole note": real page structure, real text (not a raster the client would need to OCR), and page breaks here are genuine intentional pagination the user would also see when printing/exporting, not an arbitrary cut invented by the MCP layer.

Both formats kept, scoped differently:

- **`strokes_images`**: strokes-only PNG, full note height (not the fixed 360×500 box), for handwriting-recognition use cases. Built following the exact pattern already proven live in `NoteCanvas.js`'s `_renderSelectionToPng` (used for copy-to-system-clipboard) — offscreen canvas, `MAX_SIZE` cap + scale-to-fit (same reasoning as the earlier "cap resolution, don't paginate" design decision), draw via `drawStroke`/`getThemePalette` (already exported from `noteRenderer.js`) — except bounds come from `getStrokeBounds(note.strokes)` (also already exported) covering the *whole note*, not a selection.
- **`note_pdf`**: the real PDF export, returned as an MCP `resource` content block (same mechanism already built for the `attachment` format's `pdf` kind in Phase 4a).

**Implementation**: both new formats live entirely in `mcpBridge.js` (`renderStrokesToImage`, `renderNoteToPdf`), reusing `getStrokeBounds`/`drawStroke`/`getThemePalette` from `noteRenderer.js` and `exportNoteToPdf` from `pdfExport.js` unchanged — no new drawing/export logic written, only the MCP-facing wrapper + base64 encoding. Added a small `uint8ArrayToBase64()` helper (chunked `String.fromCharCode.apply`, since there's no Node `Buffer` in the webview) for `note_pdf`'s binary output — `strokes_images` reuses the existing `fileToDataUrl`/`dataUrlToBase64` path already used by the attachment formats. Rust side: `get_note`'s `format` enum + description extended with both new values; 1 new test asserting they're advertised (26 total).

**Verified live against real notes, not just curl-shape-checking**:
- `strokes_images` on a note with substantial handwriting (spanning far more vertical space than any fixed thumbnail box) — correct `image` content block, correct `image/png` MIME, valid PNG magic bytes, and **visually confirmed** (rendered and viewed the actual image): real multi-color handwriting, full note height captured, clean white background, **no media/background pattern/typed text** — exactly the strokes-only scope intended for a handwriting-recognition source image.
- `note_pdf` on the same note — correct `resource` content block, correct `application/pdf` MIME, valid PDF magic bytes (`%PDF-`) and trailer/`%%EOF`. Visual rendering wasn't available in this environment (no `pdftoppm`/`node-canvas`), so verified structurally instead with the same library that generated it: loaded the returned bytes with `pdf-lib` and confirmed **5 real pages** at the correct A4 dimensions (595.28×841.89pt, matching `pdfExport.js`'s own constants) — strong evidence of a correctly paginated, non-corrupt document, not just "looks like a PDF."
- Error path: a note with no strokes → `get_note(id, "strokes_images")` returns a clean `isError:true` ("This note has no strokes to render"), not a crash.

**Exit — achieved:** `get_note(id, "strokes_images")` returns a valid, correctly-scoped (strokes-only), full-height PNG, visually confirmed correct. `get_note(id, "note_pdf")` returns a valid, correctly-paginated multi-page PDF, structurally confirmed correct via `pdf-lib`. Both built by reusing mature existing code with no new rendering/export logic.

#### Follow-up: `note_pdf` fails in Claude Desktop — confirmed client-side, not a NoteBerg bug

After the above verification, a real Claude Desktop session asked to read a note's `note_pdf` and got: `ClaudeAiToolResultRequest.content.0.image.source.media_type: Input is not one of the permitted values`. Investigated rather than assumed: re-curled the exact same `get_note`/`note_pdf` call against the live server and confirmed the response is still, correctly, `{type:"resource", resource:{uri, mimeType:"application/pdf", blob}}` — no `image` field, no top-level `data`/`mimeType` anywhere in it. **Our server was never the source of the bug.**

Searched and found the same failure mode independently documented: [Claude Desktop does not surface MCP `EmbeddedResource` blocks as artifacts (anthropics/claude-ai-mcp#287)](https://github.com/anthropics/claude-ai-mcp/issues/287) and [Returning an `EmbeddedResourceBlock` from a tool does not work with Claude Desktop (modelcontextprotocol/csharp-sdk#1261)](https://github.com/modelcontextprotocol/csharp-sdk/issues/1261) — Claude Desktop's/`mcp-remote`'s handling of the MCP `resource` content type is currently immature (blocks get silently dropped, or in some paths get miscoerced toward the `image` shape, which then fails validation because `application/pdf` isn't a permitted image media type — matching the exact error observed). Same category of issue as the Windows `cmd /c npx.cmd` bug and the config-file URL-support gap from Phase 3: a rough edge in the current MCP client ecosystem, not something to work around by making our server non-compliant.

**Decision (confirmed with the user): keep `note_pdf` spec-correct, document the client-side limitation.** Considered and rejected sending a non-compliant shape (e.g. faking an `image` block) just to work around today's client behavior — that would break for clients that *do* support `resource` correctly, and bakes a workaround for someone else's bug into our wire format. Documented in `documentation/mcp.md` (new "Known issue" section, linking both GitHub issues, with `strokes_images` named as today's working alternative for handwriting-focused use cases) and here.

**Exit for this follow-up:** `note_pdf`'s implementation and response shape confirmed correct via direct re-verification; the failure is isolated to the client/bridge side and documented as a known, tracked, external limitation — not left unexplained or misattributed to our code.

### Phase 4c — remaining tools ✅ done

Containment held throughout: no new data-access logic was written. `search_notes` and `get_task_markers` reuse the exact algorithms already powering the overview UI's search box and Markers tab — extracted into small exported functions rather than duplicated, so the UI and MCP bridge share one implementation.

**`search_notes(query)`** — the overview search UI's matching logic (typed content, recognized handwriting, extracted PDF text; `*`/`?` wildcard support) was inline in a DOM event handler in `overviewMode.js`. Extracted verbatim into an exported `searchAllNotes(rawQuery)`; the UI handler now just calls it. `mcpBridge.js`'s `search_notes` tool calls the same function and trims the result to a lightweight summary (`id`, `title`, `notebookId`, which sources matched) — the full note is available via `get_note` for a client that wants details.

**`get_task_markers(notebook_id?)`** — mirrors `renderMarkersTab`'s candidate-filtering (skip notes that can't have tasks without fetching them) + per-note `extractTasksFromNote()` call, minus the progressive-rendering/UI parts (no container to paint incrementally for an MCP response). `extractTasksFromNote` (already existed, just not exported) and a newly-extracted `deriveTaskLabel` (the human-readable label logic — text extracted from the note's HTML span, or recognized words matched to a stroke task's `strokeIds` — previously inline in `renderTaskItem`) are both reused as-is.

**MCP resources** (`resources/list`/`resources/read`) — notebooks and notes exposed as browsable `noteberg://notebook/{id}` / `noteberg://note/{id}` URIs, per the [MCP resources spec](https://modelcontextprotocol.io/specification/2025-06-18/server/resources). Declared capability: `{"resources": {}}` (neither `subscribe` nor `listChanged` — no server-to-client push exists, consistent with the earlier no-GET/SSE decision). Both methods need webview data (notebook/note lists), so — like `tools/call` — they're deferred out of the pure `route_mcp_message` router into a new `RouteOutcome::ReadResources` variant, then dispatched through the **same `call_tool` plumbing** used for real tools, targeting two internal-only bridge tool names (`__resources_list`, `__resource_read`) that are deliberately **not** in `KNOWN_TOOLS`/`tool_descriptors()` — reachable only via `resources/list`/`resources/read`, never discoverable or callable via `tools/call` (verified by a dedicated test). `resources/read` returns a compact JSON snapshot (metadata + typed HTML + recognized text for notes; metadata for notebooks) — not every `get_note` format, which stays behind the `get_note` tool for a client that wants a specific representation. Resource-not-found errors map to the spec's `-32002` code.

**A real (if cosmetic) bug found and fixed while building the resources error path**: `call_tool`'s error branch passed the JS bridge's raw `JSON.stringify({error: "..."})` string straight through as the error message, so every `tools/call` error text (visible since Phase 4a) was doubly-JSON-encoded — e.g. a client would see the literal text `{"error":"Note not found: x"}` instead of the clean message `Note not found: x`. This had been present and unnoticed since Phase 4a because it "worked" (a text block containing JSON-as-text is still readable), but it would have been a much more visible defect in the new `resources/read` JSON-RPC `error.message` field. Fixed at the source (`call_tool`, via a new `extract_bridge_error_message()` helper that unwraps the `{error: "..."}` envelope, falling back to the raw string for any unexpected shape) rather than patched per-callsite — both the `tools/call` and `resources/read` error paths get the fix automatically. Covered by 2 new unit tests; re-verified live that both paths now show clean messages.

**Verified live against real data**: `initialize` correctly declares `"resources": {}` alongside `"tools": {}`; `search_notes("hello")` returns real cross-source matches; `get_task_markers()` returns real tasks with correctly derived labels (e.g. recognized handwriting words matched to a stroke task); `resources/list` returns 51 real resources (5 notebooks + 46 notes) with correct `uri`/`name`/`description`/`mimeType`; `resources/read` on both a notebook and a note URI returns correct JSON snapshots; unknown URI → clean `-32002` error; missing `uri` param → clean `-32602` error.

**Exit — achieved:** all planned read tools (`list_notebooks`, `list_notes`, `get_note` with 9 formats, `search_notes`, `get_task_markers`) plus MCP resources are implemented, reuse existing UI logic rather than duplicating it, are covered by 34 Rust unit tests (all passing), and are verified live against real data — not just curl-shape-checking.

#### Follow-up: `get_task_markers` — an image fallback for unrecognized stroke tasks (two iterations; first shipped wrong)

A real Claude Desktop session surfaced a real gap: two stroke-based task markers on a "ToDo List" note had `label: null` (handwriting recognition produced no usable text for them), and Claude had no image to fall back on — the transcript shows it separately reasoning through raw stroke coordinates and landing on an explicitly uncertain guess ("my best reading is... I want to flag some uncertainty").

**First attempt (reverted): embed a `strokeImage` base64 field directly on the marker's JSON object.** Reasoning at the time: `tools/call` has one shared `content` array for the whole result, so correlating N separate MCP `image` blocks back to specific list items by position seemed fragile — keeping each marker fully self-contained (label, or `label: null` + `strokeImage`) seemed cleaner. Implemented, tested, and verified — **by decoding the base64 manually and viewing the file directly**, which is not how an MCP client consumes a tool result.

**This was wrong, and a second real Claude Desktop session proved it immediately**: asked to re-check the same tasks, Claude got stuck trying to bash-decode the `strokeImage` string and save it to a file so it could "view it properly" — it had no way to actually render a base64 PNG sitting inside a JSON *text* field. MCP clients only get native image rendering for a result that arrives as a real `{type:"image", data, mimeType}` **content block** — a JSON string field, no matter how well-formed, is just text to them. The verification gap: **I could view the image because I decoded it with my own file-reading tool, not because a real MCP client could** — the earlier "verified live" claim was true for my own inspection process, not for the client the feature is actually built for. Same underlying lesson as the `note_pdf`/`resource`-block issue from Phase 4b, and it should have been anticipated from that precedent rather than rediscovered.

**Corrected fix**: reverted `get_task_markers` to plain label-only markers (`label: null`, no image field). Added a **separate tool**, `get_task_marker_image(note_id, task_id)`, that renders just that one task's strokes and returns a real MCP `image` content block — mirroring the same reasoning already used for `attachments_list`/`attachment` in Phase 4a (list cheaply, fetch binary data through a dedicated call). A client sees `label: null` in the marker list and knows to call `get_task_marker_image` with that marker's `note_id`/`id` to view the handwriting.

**Reused, not reinvented**, in both attempts: the shared stroke-array→PNG core (bounds via `getStrokeBounds`, drawing via `drawStroke`+`getThemePalette`, scale-to-fit-within-max-size) was extracted out of `renderStrokesToImage` (the `get_note` `strokes_images` format) into `renderStrokeArrayToDataUrl(strokes, maxSize, padding)` — now the **third** place in the codebase using this exact primitive, after `NoteCanvas.js`'s clipboard-copy PNG and `overviewMode.js`'s Markers-tab mini-canvas preview (`drawTaskStrokeCanvases`).

**Verified live, this time as an actual MCP client would consume it**: called `get_task_marker_image` via the real `tools/call` JSON-RPC path (not a manual decode step) against the exact two previously-unresolved markers on "ToDo List," confirmed the response is a correctly-typed `{type:"image", mimeType:"image/png", data:...}` content block, then decoded *that* to visually confirm the pixels are correct — "Unified search in NC app" and "Full screen in NC app," both clean and legible. Error paths (missing `task_id`, unknown `task_id`) verified clean.

#### Third client-side gap in a row: Claude Desktop showed literal `[image]` text instead of the picture

Immediately after the fix above, a real Claude Desktop session called `get_task_marker_image` for both markers and saw the literal text `[image]` in place of a rendered picture — no crash, no error, just a placeholder string. Investigated rather than assumed a regression:

- Re-ran the exact same call directly against the server via curl: response is still correctly `{"type":"image","mimeType":"image/png","data":"<17696 chars of base64>"}` — one well-formed content block, nothing has regressed on our side.
- Checked Claude Desktop's own log (`%APPDATA%\Claude\logs\mcp-server-noteberg.log`): `mcp-remote` logged `result(1 blocks)` for both calls — it received and forwarded exactly one content block each time, faithfully, at the transport level. The client identifies itself as `"claude-ai (via mcp-remote 0.1.37)"` with `protocolVersion: "2025-11-25"` and an `io.modelcontextprotocol/ui` extension capability — i.e. the actual consumer here is claude.ai's own hosted tool-result rendering layer, with `mcp-remote` confirmed as a transparent, correctly-behaving pass-through, not the culprit.
- Searched for precedent: this exact symptom — an MCP `image` content block arriving correctly but the client substituting a placeholder rather than converting it to something the model can actually see — is independently documented as a recurring Claude Desktop/claude.ai gap: [MCP ImageContent returned as text in tool results instead of native image blocks (anthropics/claude-code#31208)](https://github.com/anthropics/claude-code/issues/31208) and [Image content blocks from tool results not rendered inline (anthropics/claude-ai-mcp#238)](https://github.com/anthropics/claude-ai-mcp/issues/238).

**Conclusion: this is a third, independent Claude-Desktop-side MCP content-handling gap hit in this project (after the `resource`-block issue in Phase 4b and the JSON-field/bash-decode trap earlier in this follow-up) — not a NoteBerg bug, and not something a different response shape from our server can work around**, since the block reaching the client is already spec-correct. No server-side change made. Documented here (and should be added to `documentation/mcp.md`'s known-issues list alongside the `note_pdf` caveat) so this isn't re-investigated from scratch next time it's hit. Pattern worth naming plainly: **verifying "the server sends a correct block" and verifying "a real client can actually consume it" are two different checks, and both are proving necessary, repeatedly, in this MCP client ecosystem right now** — every content type beyond plain `text` (`resource`, and now `image`) has hit a real, independently-documented client-side gap the first time it was exercised against a real client.

## Phase 5 — Observability + read-only hardening ✅ done

### Pre-work: the existing debug logger is not a valid audit-log base — clarified before implementation

Before building the "in-app activity log" from DESIGN §2, checked whether `utils/logger.js` (the existing debug logger) could serve as its foundation. It cannot, for reasons confirmed directly in the code, not assumed:

- **In-memory only, capped at 1000 entries, oldest silently evicted** (`MAX_LOG_ENTRIES` + `.shift()`). Nothing survives an app restart, and a busy session (or a client repeatedly calling `list_notes`/`search_notes`) can silently push earlier entries out with no warning — the opposite of what an audit trail needs.
- **JS-only, and explicitly, deliberately excludes Rust.** The file itself says why: `"DO NOT attach Rust logging to webview - causes severe performance issues... Rust logs will only go to stdout/terminal."` So `mcp.rs`'s own `eprintln!` calls (bind failures, eval failures, etc.) never reach this store — confirmed, not assumed, by reading `initLogger()`. This means the actual network-facing boundary (`mcp.rs`, where unauthenticated/rejected requests are handled) has no path into the in-app log at all today.
- **User-clearable via a "Clear Logs" button.** Appropriate for a debug utility; wrong for a security log a user might want to consult specifically to check "did anything access my notes" — that shouldn't be casually clearable from the same place someone clears debug noise.

**Decision: the MCP access log is a new, separate, dedicated component — not an extension of `logger.js`, and not mixed with the general debug/event log.** Confirmed with the user before implementing.

### MCP access log — design

- **New module, `src/modules/mcpAuditLog.js`**, owning its **own dedicated IndexedDB database** (not a new object store in `storage.js`'s shared schema) — keeps this fully within MCP-owned files per the containment rule, and gives the log an independent lifecycle from note-data versioning/migrations.
- **Written from `mcpBridge.js`'s `handle()` dispatch** — the single choke point every tool call already passes through, so no changes needed in `mcp.rs` at all. Logs tool name, arguments, outcome (ok/error + message), and duration. Does **not** log fetched note content/images/strokes — only what was called and with what arguments, which is the actual audit-relevant fact ("what was accessed"), not the payload itself.
- **Bounded, not unbounded**: capped at **15,000 entries**, oldest evicted first once the cap is reached — the user explicitly chose the simpler count-cap approach (same eviction shape as the debug logger) over an age-based-retention design, aware of that tradeoff, specifically because of the size concern raised up front ("we need to make sure we limit the log size in a clean way... not let it grow unbounded").
- **User-controllable, on by default**: a new `mcp_audit_log_enabled` setting (default **on** — an audit trail defaults to off would defeat its own purpose), toggle placed in Settings next to the existing MCP controls. When off, logging is a no-op; existing entries are untouched until the user explicitly clears them (clearing the audit log is a separate, deliberate action from disabling it).

### MCP access log — implementation ✅ done

- **`src/modules/mcpAuditLog.js`**: owns `openDB("NoteBergMcpLog", 1, ...)`, one `entries` object store (auto-increment key, `timestamp` index). `appendAuditEntry()`, `getRecentAuditEntries(limit, offset)` (newest-first, paginated), `getAuditEntryCount()`, `clearAuditLog()`, `isAuditLogEnabled()`/`setAuditLogEnabled()` (setting `mcp_audit_log_enabled`, default **true**). Cap enforcement (`enforceCap()`) runs after every append: if count exceeds 15,000, deletes oldest entries via a cursor over the `timestamp` index until back at the cap — chosen (confirmed with the user) as a simple count cap rather than age-based retention, accepting the same "oldest silently evicted" shape as the debug logger, just at a much higher ceiling and in durable storage.
- **`mcpBridge.js`'s `handle()`** wraps every dispatch (unknown-tool, success, and error paths) with a call to a new `logAuditEntry()` helper — measures duration via `performance.now()`, logs tool name + arguments + ok/error + duration, and is wrapped in its own try/catch so a logging failure can never break the actual tool call. Internal bridge tools (`__resources_list`/`__resource_read`) are logged under their real names too, since they're just as much "what did the MCP connection access" as any advertised tool.
- **Settings UI**: new controls in the MCP section (`settingsMode.js`) — "Log MCP access" toggle (default on), entry count display, "View access log" button, "Clear access log" button (destructive-confirm, same pattern as revoke-token).
- **Viewer**: a **dedicated** paginated table modal (`openMcpAuditLogModal()`), deliberately **not** a reuse of the existing debug-logs modal — that modal dumps its entire log into one `<textarea>`, which doesn't scale to a structured, up-to-15,000-entry store the way it just barely does for the debug logger's 1000 free-text lines. Columns: time, tool, arguments (JSON, truncated visually), outcome (OK/Error, with the error message as a tooltip), duration. Page size 50, Previous/Next controls, a live page-position indicator (`"1–24 of 24"`), and a copy-current-page-to-clipboard button. All interpolated field values (tool name, arguments, error message) go through a local `escapeHtml()` helper, since arguments/error text can contain arbitrary user-supplied content (e.g. a search query).
- **Tests**: 8 new vitest unit tests in `mcpAuditLog.test.js` (append shape, error-entry recording, disabled-is-a-no-op, defaults-to-enabled, cap eviction evicts exactly the oldest entry and lands back at the cap, clear, newest-first ordering, offset-based paging) — mocking `idb` with a small hand-rolled in-memory store (including cursor support for eviction), following the same convention `storage.test.js` already established rather than introducing a `fake-indexeddb` dependency.
- **i18n**: full English keys for all the above, propagated to the other 8 locales with English fallback text (same script-assisted process as previous phases), all re-validated as JSON.

**A real, if small, UI bug found and fixed during live verification**: the modal's Previous/Next buttons were correctly *disabled* (functionally unclickable) when there was only one page, but rendered with no visual indication of being disabled — clicking did nothing, but they looked identical to an enabled button. Root cause: the existing `.setting-item button:disabled` CSS rule only applies inside `.setting-item` elements; the modal's footer buttons live in `.modal-footer`, which had no equivalent rule. Fixed with a one-line CSS extension (`.setting-item button:disabled, .modal-footer button:disabled { ... }`) rather than a new modal-specific rule, since this is a general gap that would affect any other modal's disabled footer buttons too.

**Verified live**: made real MCP calls (`list_notebooks`, `search_notes`, a failing `get_note`) against the running server, confirmed the count in Settings updated correctly, then confirmed the actual attachments-related test traffic from earlier phases was durably present after those (24 real entries visible in the viewer, correct timestamps/tool names/arguments/outcomes/durations) — i.e. the log had already survived at least one app restart between when those entries were written and when they were viewed, since the dev instance had been recompiled/relaunched multiple times across this session. Pagination and the disabled-button fix both re-confirmed visually after the CSS change.

**Exit — achieved for the access-log piece:** every MCP tool call is durably recorded (tool, args, outcome, duration) in a dedicated, capped, restart-surviving store; the store is independent of the debug/event logger; the user can view (paginated table, not a raw text dump), disable, and clear it independently.

### Remaining Phase 5 items — resolved

- **Read-only token scope enforced end-to-end**: still moot — there are no write tools yet (Phase 6, gated behind its own consent-model design pass). Nothing to enforce a read-only *scope* against until a write tool exists to be scoped away from. Revisit as part of Phase 6, not before.
- **Rate/abuse guards on the localhost endpoint**: considered and explicitly declined for now (confirmed with the user). Reasoning: the endpoint is loopback-only (no remote attacker in this threat model), already token-protected (an unauthenticated caller is rejected before any tool runs), and currently read-only (no destructive action a runaway client could trigger). The realistic failure mode — a misbehaving/looping local client hammering the endpoint — mostly costs CPU/battery, not data exposure, and each request already serializes through one webview round-trip per Phase 1's per-request-thread design, which is itself a natural throttle. Adding a request-counting/429 layer now would be new surface (a `HashMap`/timestamp tracker in `McpState`, another failure mode to test) for a problem that hasn't actually been observed. **Decision: skip, revisit only if a real problem is observed in practice** (e.g. a client caught looping tool calls) — consistent with Phase 1's identical "don't add surface for a scenario that doesn't occur" call on the webview-not-ready probe.

**Phase 5 — fully closed.**

## Phase 5b — Multi-token support ✅ done

Prompted by a direct question after Phase 5 shipped: the token UI's single "Regenerate"/"Revoke" pair implies — correctly — that only one token can exist at a time, shared by every configured MCP client. See DESIGN.md §2a for the full rationale and design. Scope, confirmed with the user:

- Named, independently-revocable tokens (metadata list in `storage.js` settings; each secret in its own keyring entry, not one combined blob).
- Token identity threaded through the whole call path into the audit log (**confirmed to do now, not deferred** — a named token that can't be attributed in the log defeats half the point of naming it).
- Settings UI: generate-with-name-prompt, list of named tokens each with its own revoke button.
- Audit log viewer: new token/client column, attributed from the value stored on the entry itself (so history survives the token being revoked later).

### Implementation

- **Rust (`mcp.rs`)**: `McpState.token: Mutex<Option<String>>` → `tokens: Mutex<HashMap<String, String>>` (secret → name). `mcp_set_config` now takes `tokens: Vec<McpTokenEntry{value, name}>`, replacing the whole map each call (empty `value` entries filtered out, same normalize-empty-to-absent behavior as the old single-token revoke path). `has_valid_token` → `matched_token_name(request, &tokens) -> Option<String>`, comparing against every token with the existing constant-time comparison (no short-circuit on first match, so timing doesn't leak which slot matched) and returning the matched name. `call_tool` injects the matched name into a clone of the tool's `arguments` as a reserved `_tokenName` field — mirrors the existing `__mcp_content_kind` JS→Rust marker convention, but Rust→JS, chosen specifically so `eval_bridge`'s script-building and the JS-facing `handle(tool, requestId, args)` signature didn't need to widen. `dispatch_mcp_message`/`handle_mcp_post` thread the matched name through to `call_tool`. 5 unit tests rewritten/added for the new map shape (state defaults, empty-value filtering, matched-name lookup found/not-found) — all 42 Rust tests pass.
- **`mcpBridge.js`**: token metadata (`{id, name}[]`) now lives under a `mcp_tokens` storage.js setting; each secret is stored under its own keyring entry (`mcp_token_{id}`), not one shared key. `generateAndStoreMcpToken(name)` mints a new id + secret, appends to the metadata list, pushes the full set to Rust. `revokeMcpToken(id)` removes just that id's keyring entry and list row, pushes the reduced set. `handle()` destructures `_tokenName` off the incoming args before handlers see them, passing it to `logAuditEntry`.
- **`mcpAuditLog.js`**: entries gained a `tokenName` field (plain string copy, not a foreign key — so history stays attributable after a token is later revoked or renamed). 1 new vitest test added (10 total in the file).
- **Settings UI (`settingsMode.js`)**: single generate/regenerate/revoke button trio replaced with a named-token list (one row per token, each with its own "Revoke" button) plus a "Generate new token" button that prompts for a name first. New `showTextPrompt()` added to `modals.js` (a generic single-line text prompt, mirroring `showPasswordPrompt`'s structure) since no existing modal fit. Audit log viewer gained a "Token" column, backfilling to "Unknown" for older pre-multi-token entries that predate the field.
- **i18n**: full key set (token list labels, name-prompt dialog, audit log column) added to `en.json` and propagated to the other 8 locales with English fallback text, all re-validated as JSON.
- **UX polish after first live look**: the name-prompt dialog's message paragraph had cramped default `<p>`-margin spacing against the input below it — fixed with a dedicated `.modal-text-prompt-message` CSS rule. Its confirm button was relabeled "Next" (added a new `common.next` i18n key) since the dialog leads into token generation rather than being a terminal confirmation. The token-generated dialog gained an explicit "Copy" button alongside the existing proactive auto-copy-on-generate, for re-copying if the automatic clipboard write silently failed or the user wants it again.

**Verified**: all 42 Rust tests and 876 JS tests (vitest) pass; Biome lint clean on every changed file. Live-tested against the running dev app: generated a first named token ("Claude Desktop"), confirmed the Settings UI's token list showed it with a working per-row revoke button, confirmed the audit log's new Token column correctly attributed subsequent MCP calls to that name.

**Exit — achieved:** multiple independently-named tokens can exist simultaneously; each authenticates independently; revoking one doesn't affect the others; the audit log records which named token made each call.

## Phase 5c — List/read endpoint field sweep ✅ done

- **`get_task_markers`**: gained `notebookId` and `noteModified` per task — both already sitting on the fully-fetched `note` object in the existing loop; lets a client group by notebook or sort by recency without cross-referencing `list_notes`.
- Rust tool descriptions (`mcp.rs`) updated to mention the new fields on `list_notebooks`, `list_notes`, `get_note`'s `metadata` format, `search_notes`, and `get_task_markers`.

**Verified**: full Rust (42) and JS (876) suites pass, Biome lint clean; every change re-confirmed with a live MCP call against the running dev app (not just code review) before and after, comparing actual response shapes.

**Exit — achieved:** list/read endpoints return curated, AI-consumption-friendly shapes with no sync-internal noise, and expose a small set of genuinely free additional fields; nothing added that would require a new IndexedDB read or schema change.

## Phase 5d — Code-review fixes (ReDoS, deleted-note leak, revoke ordering, startup race, misc.)

A round of external code review against Phases 5b/5c surfaced several real, confirmed issues — each verified empirically or via the live running app before fixing, not taken on faith.

**`search_notes` ReDoS (critical, two rounds)**: the glob-to-regex translation (`escapeRegex(query).replace(/\*/g, ".*")`) is catastrophic-backtracking. First fix attempt (a >3-wildcard rejection cap) was itself wrong — reviewed and confirmed empirically that content *length*, not wildcard count, is the dominant variable: a 3-wildcard query against just 800 characters of non-matching content took 41 seconds (single-threaded JS, freezing the whole app), and even 2 wildcards were badly non-linear (4000 chars: 24s). **Real fix**: replaced the regex entirely with a linear two-pointer glob-matching algorithm (`wildcardMatch`/`globQueryMatches` in `overviewMode.js`) — no regex engine, no backtracking possible, confirmed via 22 parity test cases against the old behavior plus a stress test (50 wildcards vs. 500,000 characters: ~11ms). Live-verified against the real note library: the exact adversarial queries from the review now return correct results instantly. `overviewMode.test.js` added (8 tests) since no test file existed for this module.

**`get_note`/`resources/read`/`get_task_marker_image` exposed deleted (recycle-bin) notes**: `getNote()`/`getNotebook()` (`storage.js`) have no `deleted` filter (unlike every list path), so a note/notebook's id — discoverable from an earlier `list_notes` call — kept working after the user deleted it, until physically purged. Fixed via a new `getNoteOrThrow()` helper (used by `get_note` and `getTaskMarkerImage`) and an inline `deleted` check in `readResource`'s note *and* notebook branches (the notebook case wasn't explicitly called out by the review but is the identical defect). Live-verified: had the user delete two real notes ("new test", "Text Note") and confirmed `get_note`, `resources/read`, and `get_task_marker_image` all now correctly report "not found" for them.

**`revokeMcpToken` left a revoked token live if the keyring delete failed**: `deleteSecureCredential` (unlike `getSecureCredential`) doesn't swallow its own errors, and it ran first, unguarded — a throw there meant Rust's token map was never updated, so the "revoked" token kept authenticating all session while the UI showed success. Fixed by reordering: push the reduced token set to Rust first (that's what actually stops access), persist the reduced list, then best-effort delete the keyring entry in a try/catch last.

**Startup config push was an un-awaited, no-retry fire-and-forget**: `initMcpBridge()`'s push of persisted settings into Rust's in-memory state ran as an async IIFE nobody awaited; a transient failure left MCP silently disabled all session with the Settings toggle still showing "on" (Rust's actual `enabled` was never cross-checked against the persisted setting). Fixed: extracted to an exported `syncMcpConfigToRust()`, awaited from `main.js` with one retry on failure; Settings UI now computes `mcpStatusMismatch` (persisted `enabled` true but live `status.enabled` false) and shows a warning + "Retry" button when they disagree, rather than silently showing a toggle that doesn't reflect reality.

**Non-object `arguments` silently dropped `_tokenName`**: `call_tool`'s `_tokenName` injection only runs inside `if let Value::Object(map)`, so a client sending `"arguments": []` (or any non-object) passed straight through with token attribution silently lost, rather than being rejected as the malformed request it is. Fixed by validating `arguments.is_object()` in `route_mcp_message`'s `tools/call` branch, returning a clean `-32602` otherwise. New Rust test covers `[]`, `"x"`, `5`, and `null`.

**`hasMcpToken` dead code**: confirmed zero callers (Settings uses `listMcpTokens().length` instead) — removed.

**MCP audit log survived a full local-data purge**: `purgeLocalData()` (`storage.js`) has no reason to know about `NoteBergMcpLog` (separate database, by the containment rule) — but a "wipe everything local" action leaving MCP call history (note ids, search query text) behind defeats its own purpose. Fixed at the call site (`settingsMode.js`'s purge handler), not inside `storage.js` — calls `clearAuditLog()` from `mcpAuditLog.js` alongside `purgeLocalData()`, keeping the containment boundary intact.

**Checked, not reproducible as described**: the reviewed `escapeHtml(entry.errorMessage)` "renders literal 'null' in the title attribute" claim did not reproduce against the current code — `escapeHtml`'s `text ?? ""` guard already handles a `null` `errorMessage` correctly (empty string, not the literal text "null"), confirmed by direct test. No change made; noted here rather than silently ignored.

**Deferred, not fixed this round**: rejected requests (401 bad token, 503 disabled/no-token) are handled entirely in `mcp.rs` and never reach the JS audit log — the single most security-relevant signal ("who tried and failed to get in") currently leaves no trace. Fixing this means Rust calling back into the webview purely to log a failed attempt, a real architectural addition (a new callback path, plus a decision on whether to log 503s too or just 401s) rather than a same-session fix — **explicitly deferred to its own pass, confirmed with the user**, not silently dropped.

**Verified**: full Rust (43) and JS (884) suites pass, Biome lint clean, all 9 locale JSON files re-validated. Every fix in this list was verified against the actual running dev app (not just unit tests) except the `revokeMcpToken` reordering and the non-object-`arguments` rejection, which were verified via the new unit tests plus direct code inspection (simulating a keyring failure or crafting a raw malformed JSON-RPC body isn't practical through the MCP tool interface available in this session).

## Phase 5e — Live-usage bug reports (localization, stale status text, stroke-bounds margin bug) + footer indicator

Three real bugs reported after using the multi-token UI and the MCP tools live, plus a small feature request (a footer status indicator). All contained in the same MCP-owned files (`mcpBridge.js`, `footer.js`, `settingsMode.js`, `noteRenderer.js`) or general locale files, no new touch points.

**MCP settings not localized:** the entire `settings.mcp` i18n section had been left as English placeholder text (not fabricated translations) in all 8 non-English locales throughout this whole feature's development, unlike the rest of the app. Reported directly by the user running the app in German. Fixed by translating all 48 keys into all 8 locales (`de`, `es`, `fr`, `it`, `ja`, `ko`, `pt`, `zh`) — delegated to a subagent given the volume, then independently spot-checked (German and Japanese read as natural, correct technical UI text) and verified against the existing `locales.test.js` key-parity/placeholder/length-ratio suite (31/31 passing). Bonus find during that pass: a stray, incorrectly-placed `settings.recognition.serverDisabled` key (wrong section, duplicate of the real `mcp.serverDisabled` string) had leaked into all 8 locale files' working tree — removed.

**Settings status line stayed stale after disabling MCP:** unchecking "Enable MCP server" correctly pushed `enabled: false` to Rust, but the status line kept showing "Access token configured. Listening on 127.0.0.1:8765." — its text depended only on token presence, never on the enabled flag, and nothing re-rendered the section on toggle. Fixed: the status text now shows a distinct "MCP server is disabled." message whenever `mcpEnabled` is false (token/port details are now nested under an `mcpEnabled` check instead of shown unconditionally), and the toggle's `change` handler re-renders the settings panel so the correct text appears immediately.

**Stroke images had large, asymmetric blank margins:** reported with a screenshot of a `strokes_images` result showing significant blank space on the left/top/right of the actual handwriting. Root cause found in `getStrokeBounds()` (`utils/noteRenderer.js`), a shared utility also used by the overview's Markers-tab mini previews (not MCP-specific): the per-stroke half-width padding (`minX -= w; maxX += w; ...`) was applied inside the per-stroke loop, each time widening the *already-combined* running min/max from every prior stroke — so for N strokes the bounds ended up padded roughly N times over. Confirmed empirically: 100 strokes with a real ~150px ink extent produced a 350px-wide bounding box (2.3x too wide). Fixed by computing the widest stroke's half-width during the loop but applying it exactly once, to the final combined bounds, after the loop. An existing unit test (`noteRenderer.test.js`) had explicitly asserted the buggy multi-stroke behavior as "correct" (titled "...with padding applied cumulatively per stroke") — rewritten to assert the fixed values, plus a new 100-stroke regression test and a mixed-stroke-width test. Live-verified against a real note with many strokes: the rendered image is now tightly cropped, no more visible margins.

**Footer MCP status badge (new, small feature):** a small "MCP" text badge next to the sync indicator, Windows only, shown only when the server is both enabled (persisted setting) and actually running (Rust's live status) — reusing the same enabled/running distinction from the Settings status-mismatch fix above. Modeled directly on the existing `.recognition-indicator` pattern (`footer.js`): a plain DOM element inserted after `.sync-status`, toggled via `window` custom events rather than polling. Two new events dispatched from `mcpBridge.js`, both from single funnel points already used by every other MCP mutation/call path, so no new plumbing was needed there: `mcp-status-changed` (from `pushConfigToRust`, which every enable/disable/token change already calls) and `mcp-activity` (from `handle()`, the same choke point the audit logger hooks into) — the latter briefly changes the badge's text color to green (a plain CSS `color` transition, no size/scale animation, per explicit user feedback that an initial scale-pulse version felt too invasive) for 500ms on every tool call, success or failure alike.

**Verified**: full Rust (43) and JS (886) suites pass, Biome lint clean, all 9 locale JSON files valid and re-checked against `locales.test.js`. Live-verified against the running dev app: the "MCP" badge appears and pulses green on a real `list_notebooks` call; a real multi-stroke note's `strokes_images` render is now tightly cropped (before/after compared directly); German and Japanese translations read correctly in-context.
